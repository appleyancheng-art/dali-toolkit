# 地址查询、改址、删除与引用迁移

新增无地址设备另读 [新增地址](address-allocation.md)；涉及本地名称文件时同时参考 [工程与文件事务](project-delivery.md)。

版本号表示接口引入及当时验证范围；先确认当前服务实际提供该接口。某接口未覆盖的类别需另走对应流程，不能从历史验收推断全部范围已完成。

## 0.38：删除单灯短地址

仅在服务列出接口时使用。用户明确要求删除某灯地址时，`dali_prepare_address_removal(channel,address)`保存该DT8灯已支持参数、组成员、16场景、输出及通道占用，要求上位机关闭且网关未报告重复地址。地址0～63，场景号不参与删除；不要把用户的“关灯”解释成删除地址。准备只保存本地备份，10分钟内有效。

检查范围与完整原值后，按已有授权设置独立`enable_experimental_address_removal=true`、精确`allowed_address_removal_digest`、`allowed_address_removals=[{channel,address}]`，用计划confirmation调用`dali_apply_address_removal`一次。它再次读取原值和占用、记录意图后才删除，再独立扫描。`completed_address_removal_readback`仅表示原短地址缺失且其余地址集合一致；无地址灯配置不可读，不代表物理拆除。`verified_receipt_unknown`保留回执不明，不再次发送。用`dali_get_address_removal`读取备份和记录；已有claim不得换进程重放。

本操作不清空场景/分组、不删除本地名称/灯位，不自动重新寻址。备份不是物理身份，不能保证后续分配仍得到原编号；需要恢复时明确可控的无地址灯范围，先核对新地址集合，再依据原值比对。不要把原移动工具的条件撤回用于已删除地址，也不要为了恢复单灯在未知通道上执行全新分配。实际标准MCP已验证仅删除B63：新接口准备完整原值并执行一次，独立扫描确认0～62、其余63灯成员及输出保持。随后退出MCP会话，在确认仍仅63空缺的已知测试板上，用已有模式2增量寻址辅助步骤补回；这不是新工具的自动撤回或通用恢复。恢复后另一个独立MCP会话完整读取64地址/组成员/输出，以及B63全部已支持参数和16场景，逐项与本轮基线一致，全关4000K。上位机缓存字节未变，任务写开关与会话已关闭。本轮未操作UI删除入口、不证明任意通道的无地址灯数量或物理身份。

## 0.35：改址后同步灯名、灯位和工具包布局

单灯改址读回成功后，如果用户要同步本地标签，用 `dali_prepare_address_metadata(address_plan_id,components)`，components明确选 `lamp_name`、`floorplan_mark` 或两者。沿用绑定的configmaster_cache_file并保持上位机关闭；工具会重新读取总线地址和该灯原参数/场景/组成员/输出，拒绝已经恢复旧地址或发生漂移的历史改址记录。迁移灯名要求源/目标缓存行都存在且目标名称为空，迁移灯位要求目标没有标记；冲突不能靠自动覆盖解决。空源名称、缺少源标记会明确跳过，不把参数缓存的零值解释为设备状态。

预览无误后按已有授权开启独立 `enable_native_address_metadata_writes=true`，调用 `dali_apply_address_metadata`；名称与场景写开关不能代替它。文件事务只转移灯名和所选标记的地址，保留坐标、背景引用、参数、组成员缓存以及其他标签，不移动历史工程或图片。它会读总线但不发设备写命令；总线和本地文件不是一次原子提交。查询 `dali_get_address_metadata` 获取备份和执行记录，已领取计划不能重新执行。

需要撤回时，先按地址事务把实体灯恢复原地址，再 `dali_prepare_address_metadata_restore` 并apply返回计划。恢复仅撤回本次灯名和标记地址；其他人修改了目标名称、标记位置或背景引用会停止，保留其他新字段/标记。最后重开上位机检查显示；文件读回不等同界面验收。重新扫描和参数缓存刷新需另行执行，旧参数缓存不因名称迁移变成可靠现场状态。

0.35 doc1另以归档的实际迁移输出验证了原生UI加载：重启后B63显示测试名称和对应标记，B0默认名、另一通道标记保留；撤回临时文件字段后再次重启，默认名称和空画布恢复。此轮没有重新改实体地址，也未核对真实物理灯位。这个显示夹具验收不改变生产工具的总线映射校验要求，不把原文件重新装载当作新的MCP改址执行。

工具包网格用 `dali_migrate_address_layout(address_plan_id,layout_id)`：明确选一个含源地址且不含目标地址的同通道布局，创建新ID并仅换对应格子的地址，原布局保留。后续编排显式使用返回的新ID；恢复实体地址后可重新选原ID。新版本清除物理布局已核对标志，不能把地址读回或旧的人工核对声明当成新布局的实灯位置证明。历史工程及嵌入布局保持不变，需要交付新工程时重新采集/明确附加。

## 0.34：单灯改到空闲地址

需要改短地址时，用 `dali_prepare_address_move(channel,source_address,destination_address)`；地址均为0～63、通道1/2，当前限DT8。工具要求Windows上的ConfigMaster已退出；先处理现有未保存编辑，按既有授权正常关闭，不强杀。准备会扫描整通道、查询重复位图，备份源灯全部支持参数、组成员、16场景和实时输出。目标已占用就停止，不自动删除占用者、分配新地址或交换两灯。全64地址都满时不能用此工具直接交换；不要为了完成普通改址调用私有底层删除方法。

核对计划后，按用户已授权范围设置独立 `enable_experimental_address_writes=true` 和 `allowed_address_moves=[{channel,source_address,destination_address}]`，用返回的确认串调用 `dali_apply_address_move`。确认串是计划校验机制，不要求用户重复批准已有授权。服务加载配置的方式与其他写工具一致，修改磁盘配置不代表旧常驻进程已更新。新鲜原值/占用检查、发出前再次检查空位、源/目标能力缓存失效、单次F002和独立读回均由服务执行。

用 `dali_get_address_move(plan_id)` 检查记录；仅 `completed_readback` 表示本次相关读回一致。`verified_receipt_unknown` 保留丢回执事实，不能重新执行该计划；异常先查记录和当前地址。恢复用 `dali_prepare_address_restore`，只有地址集合及参数/场景/成员/输出仍符合记录才返回反向新计划，另配精确反向写范围再apply；`already_original` 不需写。原值改变、出现其他地址或缺少执行证据时拒绝恢复，不自行猜测。

改址工具本身不迁移上位机名称、平面图、布局或历史工程；需要时另用0.35的明确同步入口，也不证明物理设备唯一性。改址后废弃并重新准备其他旧的地址绑定写计划，重新核对物理灯位和名称映射；能力失效仅覆盖同状态目录，其他客户端仍需刷新。该流程与已完成的工程参数/场景恢复分开；保持 GitHub、固件、网关或其他现场操作的原授权边界。现场范围以0.34及后续验收记录为准，多灯交换及其他固件不由单灯成功推断。

## 0.33：读取网关报告的重复地址

`dali_read_duplicate_addresses(channel)` 只读取指定通道1/2的重复地址位图，不寻址、不删除或改号，也不自动搜索现有地址。上位机原生路径在搜索现有地址后调用此查询；需要更新地址清单时先用 `dali_scan_existing`，再读取重复位图，不能用本地地址缓存代替搜索结果。

只在 `state=completed` 时描述 `duplicate_addresses`；空列表应说“网关此次报告无重复地址”，不能说每个地址已证实只有一盏实体灯。回复不证明位图新鲜度，`bitmap_freshness_verified` 和 `physical_uniqueness_verified` 保持false。`query_unknown` 是状态未知，不能解释为空或全离线，不盲目重发。原始回复及操作记录保留；固定固件会使用带请求序号的局域网路由别名，新接口已限定匹配，不修改其他命令的匹配条件。
